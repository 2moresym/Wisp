WISP AI HANDOFF / PROJECT MEMORY
================================

Repository: 2moresym/Wisp
Goal: Minimal-overhead Windows x86_64 game compatibility layer for Linux.
Language: Rust-first. Small C/C++ glue only where native Linux subsystem FFI is appropriate.
Scope: 64-bit Windows games. Not a general Win32 compatibility layer. 32-bit/WoW64 and anti-cheat are out of initial scope.

IMPORTANT FOR ANY AI TAKING OVER
--------------------------------
1. Work directly from the current GitHub repository/state. Do not assume this is a fresh project.
2. Inspect existing code and git history before redesigning anything.
3. Do not rewrite working subsystems just to change architecture.
4. Preserve Windows-compatible semantics over superficial API breadth.
5. Prefer small/medium commits for risky runtime changes. Every meaningful commit should build and test.
6. Never claim a subsystem is complete when it is only a Linux-backed foundation.
7. The project owner wants eventual game testing as soon as the runtime is capable, but correctness of the loader/thread/ABI foundations comes first.
8. Wisp is Rust-based. Python may be used only as external analysis/tooling; project implementation belongs in Rust except intentional native glue.

CURRENT ARCHITECTURE
--------------------
Workspace crates:
- wisp-core
- wisp-pe-loader
- wisp-syscall
- wisp-loader-cli
- wisp-glue-c
- wisp-window
- wisp-runtime

wisp-core contains the runtime foundation:
- handle
- loader state machine
- module registry/dependency graph
- peb
- process/thread lifecycle
- sync/futex foundation
- teb
- tls
- vfs

wisp-pe-loader is responsible for strict PE64 parsing/validation and image mapping.

wisp-runtime is the higher-level loader/runtime bridge:
- DLL search/admission
- import metadata
- export metadata
- runtime loader
- builtin module lookup
- Win32 foundation
- Windows x64 ABI thunk bridge

wisp-syscall exposes NT-shaped entry points.
wisp-window provides native Wayland/X11 windowing.
wisp-glue-c is deliberately tiny native C glue.
wisp-loader-cli is the diagnostic/loader front-end.

WHAT IS ACTUALLY WORKING
-------------------------
PE loader:
- PE32+ / AMD64 parsing
- strict bounds/checked arithmetic
- section validation
- relocation groundwork
- preferred-base mapping with relocation fallback
- dependency metadata parsing
- dependency-free PE fixture execution
- original fixture has executed and returned 42
- PE entry invocation uses Windows x64 `win64` ABI

Memory:
- mmap-backed image mapping
- mprotect-backed protection changes
- basic VirtualAlloc / VirtualProtect compatibility foundation
- full Windows MEM_RESERVE/MEM_COMMIT/MEM_RELEASE semantics are NOT complete
- VirtualProtect does not yet track/report the true previous protection

Process / threads:
- WispProcess exists
- Linux-backed thread creation using std::thread exists
- Running/Exited state tracking
- wait/join and close lifecycle
- thread bootstrap installs a Wisp TEB
- panic-safe transition to Exited
- recyclable handle allocation with overflow protection
- this is NOT yet a full Windows NT thread implementation

TEB / PEB / TLS:
- x86_64 Linux GS-based TEB installation
- pinned TEB backing storage
- lifetime-bound TEB guard
- PEB anchor referenced from TEB
- stack bounds discovered from pthread attributes
- LastError storage
- TLS manager with process-wide index allocation
- per-thread inline TLS slots and expansion storage
- GS guard only restores its previous base when the live GS still equals its installation base
- TEB is intentionally partial/opaque; only explicitly implemented fields are contractual

Synchronization:
- WaitWord spin-then-futex foundation
- wait re-checks after wakeups
- NTSYNC backend exists and is optional when /dev/ntsync is available
- full Windows WaitOnAddress/SRWLock/CRITICAL_SECTION semantic compatibility is NOT complete

Handles:
- WispProcess has a Handle -> WispThread map
- HandleTable recycles released values
- null handle is reserved
- allocator refuses 32-bit wraparound
- generic typed NT object table with access masks/refcounts is NOT complete

Module / loader state:
- ModuleRegistry with dependency graph
- cycle detection
- dependency-first initialization ordering
- loader state machine enforces canonical phase transitions
- export metadata supports name and ordinal lookup
- runtime DLL path lookup is case-insensitive
- RuntimeLoader recursively discovers/maps DLL dependencies
- RuntimeLoader registers loaded modules
- RuntimeLoader can parse exports and resolve imported symbols
- RuntimeLoader patches IAT entries
- RuntimeLoader now resolves imports for ALL loaded native modules, not only the root EXE
- forwarded exports are represented and recursively resolved when their target module is already loaded
- full DllMain/TLS/CRT integration is NOT complete

VFS:
- CaseMap / case-insensitive directory lookup foundation
- exact-name lookup wins
- lazy population and invalidation
- full Windows path semantics and application-layer VFS integration are NOT complete

Windowing:
- native Wayland MVP
- native X11 MVP
- backend detection
- close/resize/input event foundations
- native protocol handles exposed for future WSI
- Wayland smoke path uses SHM rather than Vulkan
- native Vulkan WSI is NOT complete
- input semantics are NOT complete

DLL / import / export / ABI:
- import descriptors and 64-bit thunk metadata
- export directory parsing
- named and ordinal exports
- DLL dependency resolution groundwork
- builtin ntdll/kernel32 recognition
- Windows x64 `win64` entry-point calling convention
- C `ms_abi` thunk bridge compiled by wisp-runtime/build.rs
- Rust implementation entry points behind the ABI bridge
- rigorous real imported-PE execution fixture is STILL NOT COMPLETE

CURRENT CLI
-----------
`wisp-loader-cli` now accepts:
- `wisp <game.exe> --inspect` for metadata-only inspection
- `wisp <game.exe> --load` (default) for runtime dependency loading/import binding
- dependency-free binaries retain the existing map + entry-point smoke execution path

Do NOT claim `--load` means the program can already launch a real game; it prepares/maps/binds the runtime but Windows startup semantics are still incomplete.

- OpenGL/WGL support is not implemented.
- DXVK integration is not implemented.
- VKD3D-Proton integration is not implemented.
- Anti-cheat is out of scope initially.

AUDIT ITEMS STILL WORTH REVIEWING
---------------------------------
- `current_teb_base()` still collapses ARCH_GET_GS errors to a null pointer; eventually make an explicit fallible TEB-access API for diagnostics/runtime correctness.
- Generic NT object manager with object type/refcount/access rights is still needed.
- VirtualProtect needs virtual-region metadata if true previous protection semantics are required.
- TEB remains intentionally partial; do not promise arbitrary Windows TEB offsets.
- `wait_timeout` saturation for pathological `Duration` values can be tightened.
- IAT patch protection currently changes whole 4 KiB pages and restores based on one containing section; mixed-section pages need a more precise protection tracker before production-quality memory semantics.
- RuntimeLoader currently does not roll back partially patched IATs if a later binding fails.
- Forwarded-export parsing/resolution needs stronger fixture coverage, including API-set style cases.

TESTING RULES
-------------
Run from the repository directory; do not assume a hardcoded local path.
Primary checks:
  cargo fmt --all
  cargo build --release
  cargo test --release

For PE changes, run the PE fixture when available.
For ABI changes, test through a real Windows-x64-call-compatible function pointer.
For window changes, run the relevant Wayland/X11 smoke test on the host.
Never suppress warnings merely to make output look clean when they may indicate an ABI/FFI problem.
